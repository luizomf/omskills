# Resolving Merge Conflicts

1. **Discover operation and baseline.** Record Git status and the exact pre-existing staged, unstaged, and untracked work before changing anything. Determine whether this is an active merge or rebase, then inspect its state, todo list when present, both commit ranges, and every unmerged path. Also search the established file scope for complete conflict-marker groups. A standalone conflict-marker cleanup is valid even when no Git operation is active; do not reject or omit it merely because the unmerged-path inventory is empty.
2. **Determine every resolution before editing.** For every unmerged hunk and standalone marker group in scope, inspect both source versions and the commits that introduced them, then trace originating pull requests, issues, Tickets, Specs, ADRs, documentation, and relevant history. Establish a source-supported resolution for every in-scope conflict before editing any file, preserving both intended behaviors when they can coexist. This prevents a later indeterminate hunk from leaving partial edits. If any intent remains indeterminate or a resolution would exceed established scope, stop and report the exact blocker with the operation, worktree, and index unchanged from the recorded baseline.
3. **Edit only established resolutions.** Apply the complete resolution plan without touching unrelated paths. Make ordinary implementation decisions required by the established intent. Limit any additional fix to a failure caused by the merge or rebase, and determine that fix from the same project sources before applying it. Re-inventory conflict markers after editing and stop if the result exposes an unresolved or previously undiscovered intent question.
4. **Run applicable checks.** Discover the repository-defined checks and order from its instructions, changed-unit documentation, test layout, scripts, and configured automation. Run only repository-defined checks that apply to the resolved paths. Fix only failures caused by the merge or rebase; report unrelated failures without changing them.
5. **Stage selectively and inspect.** Only conflict resolutions and intentional merge-caused fixes may be newly staged. Use explicit paths or hunks, such as `git add -- <path>`, `git rm -- <path>`, or `git add -p`; never use `git add -A`, `git add .`, `git commit -a`, or an equivalent broad operation. Compare `git status --short` and the complete `git diff --cached --` with the recorded baseline after staging and immediately before continuation. Verify that each newly staged change belongs to the resolution plan or an intentional merge-caused fix and that unrelated work did not change.

   Preserve an unrelated change that was already staged at the baseline without allowing it into the merge or rebased commit. If active-operation continuation would include that change, or could overwrite or be blocked by unrelated work, safeguard the exact baseline outside the operation using explicit path inventories and binary-safe patches or copies. Temporarily remove only the safeguarded paths from the operation's index and worktree, inspect the staged diff again, keep the safeguard through every rebase step, then restore its exact staged, unstaged, and untracked state after the whole operation. Verify the restored state against the baseline and remove the safeguard. Stop instead of continuing if exact preservation and restoration cannot be demonstrated.
6. **Finish the active operation or cleanup.** Run `git merge --continue` or `git rebase --continue` only after all resolutions are source-determined, applicable checks pass, the staged diff has been inspected, and unrelated work is protected. If Git requires a direct merge commit, create only that merge commit. For a rebase, repeat the discovery-through-inspection process for each subsequent conflict and restore safeguarded unrelated work only after Git reports the full rebase complete. For standalone cleanup, do not invent a merge, rebase, or commit; report the resolved marker paths and leave all unrelated baseline state untouched.
