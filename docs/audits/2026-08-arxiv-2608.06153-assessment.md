# Assessment of “Learning Globally Reusable Skills for Coding Agents” for omskills

> **Executive verdict — mostly on the right track, but not validated by this paper.** Omskills already treats skills as a curated system rather than unrelated prompt fragments: it keeps one synchronized catalog, records load-bearing composition rules, separates user-level skill availability from repository-specific contracts, uses progressive disclosure, and requires deterministic repository checks. Those choices are directionally consistent with the paper. The paper does **not**, however, show that installing every skill globally is optimal, that global Pi instructions are harmless, or that this catalog improves general coding work. Its “global” means optimizing the **whole skill bank and its relationships**, while retrieving a relevant subset for each task—not user-account-wide installation. The largest evidence gap here is behavioral: omskills checks structural consistency and individual delivery workflows, but has no held-out replay suite showing that skill edits generalize without regressions.

**Assessment basis.** Paper version: arXiv v1, submitted 6 August 2026.[^paper] Repository snapshot: `main` at `16da1e7`, inspected 7 August 2026. The public issue query returned no open issues at assessment time.[^open-issues] Conclusions below are explicitly labeled as paper evidence, repository evidence, or inference.

## What “global” does—and does not—mean

| Layer | Meaning in this assessment | Evidence |
| --- | --- | --- |
| **GSE’s “globalized” evolution** | Updates are evaluated against the whole skill bank: a Skill Relation Graph (SRG) represents dependency, co-usage, and conflict; case-specific updates are consolidated and replayed before acceptance. It does **not** mean installing prompts globally on a workstation. | Paper §§3.2.2–3.3.2.[^srg][^generalization] |
| **GSE execution** | The paper formalizes per-task retrieval of a relevant subset, \(S_x \subseteq D\), from the bank. It does not inject every full skill into every task. | Paper §2.1.[^execution] |
| **Omskills user-level installation** | The installer links active skills to a shared user-level directory. Supporting harnesses keep each active skill’s name, description, and location in system context, then load the full `SKILL.md` only after selection. | [`README.md:100-129`](../../README.md#L100-L129); [`scripts/link-skills.sh:4-15`](../../scripts/link-skills.sh#L4-L15). |
| **Repository-scoped control** | Each consuming repository records tracker, label, domain-doc, and ADR rules locally; setup inspects repository evidence and obtains approval before writing that configuration. | [`setup-omskills/SKILL.md:18-33`](../../skills/engineering/setup-omskills/SKILL.md#L18-L33), [`78-117`](../../skills/engineering/setup-omskills/SKILL.md#L78-L117). |
| **Global Pi/user instructions** | These are a separate harness baseline, not an omskills manifest entry or a GSE concept. This assessment inspected only their role at a safe high level and does not publish private configuration. The paper did not evaluate Pi or user-level instruction stacks. | Local public-safety boundary: [`AGENTS.md:139-146`](../../AGENTS.md#L139-L146). Paper harnesses: §4.2 and §4.5.[^agents] |

## What the paper actually establishes

### Research question and method

GSE asks whether skill evolution works better when updates preserve whole-bank compatibility and are generalized beyond the execution traces that produced them. It diagnoses failed traces, proposes structured updates, propagates effects through an SRG, validates the originating case, clusters related proposals, abstracts reusable capabilities, and accepts a candidate bank only when relevant historical replay preserves or improves performance.[^approach][^generalization]

The evaluation is substantial but narrow:

- **Bug-revealing test generation:** 108 triggerable focal methods from 9 Java projects derived from Multi-SWE-Bench.[^test-data]
- **False-positive bug-report filtering:** 500 reports—132 confirmed bugs and 368 false alarms—from 8 proprietary Go repositories.[^filter-data]
- **Protocol:** one project is held out while the remaining projects evolve the bank, testing cross-project transfer without using held-out cases during evolution.[^protocol]
- **Harness/model controls:** OpenHands and an extended mini-SWE-agent use the same tools, environment, DeepSeek-V4-Flash model, and per-task budget across compared methods; the implementation also evaluates one proprietary industrial agent.[^agents][^industrial]
- **Baselines:** vanilla agents, 17 skills manually consolidated by six senior software-quality engineers, Live-SWE-agent, and Trace2Skill.[^baselines]
- **Outcomes:** precision, recall, and F1 for detecting the ground-truth bug or classifying a report.[^metrics]

### Exact headline findings

| Setting | Base F1 | Human-skill F1 | GSE F1 | Source |
| --- | ---: | ---: | ---: | --- |
| Test generation, OpenHands | 0.08 | 0.16 | **0.31** | Table 1.[^table1] |
| Test generation, mini-SWE-agent | 0.28 | 0.26 | **0.38** | Table 1.[^table1] |
| False-positive filtering, OpenHands | 0.37 | 0.42 | **0.70** | Table 2.[^table2] |
| False-positive filtering, mini-SWE-agent | 0.36 | 0.38 | **0.46** | Table 2.[^table2] |
| Industrial filtering agent | 0.43 | 0.44 | **0.71** | Table 5.[^industrial] |

Two details matter for omskills:

1. Human-written skills were not uniformly beneficial: on mini-SWE-agent test generation they reduced F1 from 0.28 to 0.26, while GSE reached 0.38. The paper attributes uneven human-skill gains to generic guidance and harness capability differences; this is evidence against assuming that curation alone guarantees benefit.[^table1]
2. The ablation supports both mechanisms under the tested conditions. Removing either SRG or generalization reduced test-generation F1 from 0.31 to 0.27; for filtering, removing SRG reduced F1 from 0.70 to 0.59 and removing generalization reduced it to 0.54.[^table3]

The gains are not free. GSE evolution averaged 401.55K tokens per case, 12.28% above Trace2Skill. GSE task execution averaged 593.21K tokens per case, 21.2% above the vanilla agent, although it used fewer tokens than the three other skill-based methods in that experiment.[^table4]

### External-validity boundary

The authors test two defect-focused tasks, Java and Go, two open-source harnesses, and one proprietary harness; the controlled open-harness runs use the one disclosed base LLM, DeepSeek-V4-Flash. They explicitly retain external-validity concerns across agents, languages, and software-engineering tasks.[^agents][^threats] Holding out projects supports **cross-project transfer within those two tasks**; it does not establish transfer to implementation, planning, teaching, architecture design, multi-agent orchestration, Pi, Codex, Claude, or arbitrary user-level instructions. This second sentence is an inference from the stated experimental boundary, not a result the paper measured.[^tasks][^agents][^threats]

## What is actually risky or unsupported

1. **Unsupported claim: “the paper proves our global setup is good.”** It does not. GSE studies automatic evolution plus task-specific retrieval; omskills is a manually curated, broadly scoped bank with conditional loading.[^execution][^approach]
2. **Behavioral regression risk.** Structural checks can prove that all 25 entries are synchronized and safely linked, not that a changed skill improves representative tasks or leaves unrelated workflows intact.[^table3] The distinction follows from what [`check-catalog.py:42-124`](../../scripts/check-catalog.py#L42-L124) and [`test-link-skills.sh:14-89`](../../tests/test-link-skills.sh#L14-L89) actually assert.
3. **Implicit relationship risk.** Load-bearing composition exists in prose and ADRs, but a local skill edit can still change an assumption used elsewhere without a complete dependency/co-usage/conflict check. The paper’s ablation makes this a credible concern under its tasks; applying it to omskills is a plausible extrapolation, not direct proof.[^srg][^table3]
4. **Discovery/context risk.** Every active skill is model-discoverable even where the README categorizes many as “User-invoked.” That may be a valid routing choice, but the paper’s model retrieves a relevant subset and provides no evidence that exposing all 25 descriptions on every session is optimal.[^execution] Repository evidence: [`README.md:150-191`](../../README.md#L150-L191) and [`check-catalog.py:82-86`](../../scripts/check-catalog.py#L82-L86).
5. **Private-trace risk if GSE-like replay is adopted.** The paper captures reasoning, commands, paths, and environment feedback before simplification. Doing that locally could collect proprietary code, secrets, or personal data; omskills’ public boundary therefore must remain stricter than a naive trace store.[^trace] Repository boundary: [`AGENTS.md:139-146`](../../AGENTS.md#L139-L146).

## Prioritized recommendations

| Priority | Recommendation | Evidence class |
| --- | --- | --- |
| **P0** | **Do not rewrite the catalog or disable global installation because of this paper.** Keep the current separation: user-level availability, conditional full-body loading, and repository-scoped `AGENTS.md`/domain/ADR contracts. | **Evidence-bounded conclusion:** the paper did not test this deployment choice.[^execution][^agents] |
| **P1** | **Add a small, public-safe behavioral replay/ablation protocol before the next material skill-bank redesign.** Use a few representative historical tasks with executable acceptance checks; compare baseline, global metadata only, relevant skill loaded, and candidate bank; record success, wrong-skill activation, conflicts, tokens, and cost. Hold out at least one repository or task family from skill editing. Store only sanitized prompts/results, never private traces. | **Direct principle, extrapolated implementation:** replay and held-out evaluation drive GSE; the exact omskills protocol is proposed here.[^generalization][^protocol][^table4] |
| **P1** | **Inventory only load-bearing inter-skill edges—`depends on`, `co-uses`, and `conflicts with`—and make the smallest existing catalog check validate them.** Start from current hard dependencies and orchestration composition; do not build a graph service or DSL. | **Plausible extrapolation:** SRG ablation is positive, while omskills already has a simpler static catalog and ADR model.[^srg][^table3] |
| **P1** | **Enforce the existing promotion rule with durable evidence.** For each newly discoverable skill, retain the observed-use and maintainer-approval record; for material edits, retain replay evidence showing no relevant regression. | **Repository contract plus paper support:** [`AGENTS.md:62-69`](../../AGENTS.md#L62-L69); replay rationale in §3.3.2.[^generalization] |
| **P2** | **After measurement, review the README’s “User-invoked” active skills for true user-only status.** Demote only skills whose discovery has no measured benefit or causes misrouting; do not infer that all 25 should be hidden. | **Local hypothesis, not a paper result:** current discovery state is documented at [`README.md:121`](../../README.md#L121) and enforced by [`check-catalog.py:82-86`](../../scripts/check-catalog.py#L82-L86). |
| **P3** | **Consider automated trace-derived evolution only if manual maintenance becomes a demonstrated bottleneck and a privacy-safe replay corpus exists.** | **Deliberately deferred:** GSE’s implementation adds an update agent, SRG, clustering, replay, SQLite state, and Git worktrees; current repository rules reject infrastructure for deferred needs.[^approach][^implementation] [`AGENTS.md:11`](../../AGENTS.md#L11). |

## Overreactions to avoid

- Do not read “global” as “put every full skill or every repository rule into one global prompt”; the paper uses relevant-subset retrieval.[^execution]
- Do not replace repository tests, specs, reviews, or ADRs with an SRG; GSE’s replay validates task outcomes, while those artifacts establish local contracts and executable correctness.[^generalization] Repository source-of-truth split: [`AGENTS.md:36-46`](../../AGENTS.md#L36-L46).
- Do not auto-edit skills from single failures. GSE rejects ineffective local updates, consolidates multiple proposals, and replays historical cases before integration.[^proposal-validation][^generalization]
- Do not claim universal generalization from two tasks, two languages, two open harnesses, one proprietary harness, and one disclosed base LLM for the controlled open-harness runs.[^tasks][^agents][^threats]
- Do not publish raw agent traces or private global configuration to reproduce the paper. The repository explicitly forbids those artifacts.[^trace] [`AGENTS.md:139-146`](../../AGENTS.md#L139-L146).
